# 개발 규칙

## 기본 개발 흐름

1. GitHub Issue로 작업 범위를 확정한다.
2. Issue 번호 기반 브랜치를 만든다.
3. 구현 및 테스트를 진행한다.
4. 한글 커밋 메시지로 변경사항을 기록한다.
5. 원격 브랜치에 push한다.
6. Pull Request를 생성한다.
7. 테스트 및 변경사항을 검토한다.
8. squash merge한다.
9. 필요하면 관련 문서를 갱신한다.

## 브랜치 이름

코드 식별을 위해 브랜치명은 영문 kebab-case를 사용한다.

예:

- `feature/1-wage-calculation-engine`
- `feature/2-room-storage`
- `fix/12-night-shift-boundary`
- `docs/project-foundation`

## 커밋 메시지

커밋 메시지는 **한글**로 작성한다.

예:

- `급여 계산 엔진 기본 구조 구현`
- `야간근로 경계값 테스트 추가`
- `근무 기록 Room 저장 구조 추가`
- `실시간 급여 화면 오류 수정`

불필요한 영문 conventional commit prefix는 사용하지 않는다.

## Pull Request

PR 제목과 설명은 기본적으로 한글로 작성한다.

PR에는 최소한 다음 내용을 남긴다.

- 무엇을 구현했는가
- 핵심 구현 방식
- 어떻게 검증했는가
- 남은 문제나 후속 작업이 있는가

## 테스트 원칙

급여 계산처럼 제품 신뢰성에 직접 영향을 주는 로직은 UI보다 테스트를 먼저 우선한다.

특히 다음 경계조건을 자동 테스트한다.

- 자정 통과
- 야간 시작/종료 경계
- 휴게와 야간구간 중첩
- 여러 휴게
- 조건 적용/미적용
- 잘못된 시간 데이터

## 아키텍처 원칙

급여 계산 도메인은 다음 Android 요소에 의존하지 않도록 한다.

- Compose
- Activity
- ViewModel
- Room
- Android Context

UI와 저장소가 바뀌더라도 계산 규칙을 독립적으로 테스트할 수 있어야 한다.

## 범위 관리

v1.0에서는 기능을 많이 넣는 것보다 실제 출시가 우선이다.

제품 기획서의 v1.0 제외 항목은 별도 근거 없이 개발 중 끼워 넣지 않는다.
